# H2 屏幕内容宿主（lcl-display-host）

把冷头屏幕（H2，480×480）的画面渲染从后台服务里搬出来，做成一个**独立进程**。
后台服务只留一条传输链路：宿主画好 JPEG 交过来，服务推屏。

```
 ┌────────────────────┐   GetConfig / GetStatus（≤1 秒一次）
 │ lcl-display-host   │──────────────────────────────┐
 │  解码、裁方、旋转、 │                               │
 │  主题渲染、压 JPEG  │   SubmitLcdFrame { jpeg }     ▼
 └────────────────────┘────────────────────────►┌──────────────┐
        不碰 USB                                 │  lcl-daemon  │
                                                │ 信箱只留最新 │
                                                │ 一帧，无队列 │
                                                └──────┬───────┘
                                                       │ push_jpeg
                                                       ▼
                                              H2 冷头 0x1CBE:0xA034
                                              （方屏 LCD-S，圆屏 0xA021）
```

## 为什么分开

- 后台服务是常驻的设备守护进程，屏幕渲染（解码 + 编码 + 主题绘制）是纯 CPU 工作，
  和设备控制混在一起会让控制循环被拖慢。
- 画面内容以后可能来自别的来源（外部内容进程、录制回放、远程画面），
  先把“内容”和“传输”之间的缝留出来。
- 宿主是普通用户进程：崩了不影响设备控制，冷头该转泵还是转泵。

## 边界：谁碰 USB

| 东西 | 谁碰 | 说明 |
| --- | --- | --- |
| H2 冷头 `0x1CBE:0xA034` / `0xA021` | 只有 `lcl-daemon` | USB 句柄一直在 `H2Slot` 里，宿主只送 JPEG |
| 8.8 面板的直连接口 `0x1CBE:0xA088`（LP 那条路） | 只有 `lcl-daemon` | 8.8 的画面仍然走它自己的直连通道，不经过宿主 |
| 8.8 灯环 `0x0416:0x8050` | 只有 `lcl-daemon`（`ring_service`） | 宿主不认领这个 PID，也不发灯效包 |

**宿主一个 USB 设备都不打开**，只和后台服务说命名管道（`\\.\pipe\lconnect-lite`）。
它既不枚举设备，也不会抢 LP / 8.8 的 PID。

## 协议

宿主只用三条请求（都在 `lcl_core::ipc` 里）：

| 请求 | 方向 | 说明 |
| --- | --- | --- |
| `GetConfig` | 宿主 → 服务 | 要 `config.lcd`（模式、路径、旋转、帧率、主题、亮度…） |
| `GetStatus` | 宿主 → 服务 | 要状态（水温、泵速、风扇、CPU/GPU），主题要用 |
| `SubmitLcdFrame { jpeg }` | 宿主 → 服务 | 交一帧 480×480 的 JPEG |

服务端的信箱（`Shared.lcd_frame`）**只保留最新一帧**：宿主推得再快也不会堆积，
后到的帧直接盖掉前一个。服务端的校验：

- 必须是 ≤ 512 000 字节的基线 JPEG，SOF 里的宽高都必须是 480×480，头尾要对；
- 屏幕模式是“未控制”时直接拒绝（未托管的屏幕不接收外部画面）。

传输层（`crates/lcl-daemon/src/lcd.rs`）拿到这一帧之后：

1. 冷头代次变了（重新打开、推过灯圈）就先 `lcd_init()`，再推一张全透明 PNG 清掉叠加层；
2. 亮度 / 离线时钟变了才下发；
3. 换了画面就推；同一张画面每 30 秒也重推一次（防止设备自己切回它的画面），
   推完把这一帧留作底，冷头重新初始化后可以重推；
4. 屏幕命令失败就丢掉句柄，交给控制循环重新打开。

**未托管（Unmanaged）时完全不碰屏幕**：不初始化、不推叠加层、连已经提交的那一帧也不推。

## 宿主的行为

- **配置轮询 ≤ 1 秒**：默认 500 ms（`--poll-ms`，上限 1000）。
- **只读用户指定的东西**：只有配置里指向的图片 / GIF 才会被打开，
  而且只在路径或相关配置变了的时候重新读、重新解码；平时复用已经解好的帧。
- **媒体体积上限**：单个文件 ≤ 32 MB，超了直接报错不加载；GIF 解出来超过 150 帧就抽稀。
- **帧率上限 5 fps**（`MAX_FPS`）：GIF 按 `min(cfg.max_fps, 5)` 解帧，
  发送间隔不短于 200 ms。屏幕只有 480×480，再快只是白占 USB 带宽和解码 CPU。
- **主题仪表盘最多 1 fps**：读数和外观都没变就不重画、不重发。
- **静态图每 30 秒重发一次**：防止设备自己切回别的画面。
- **失败退避**：后台服务没起、管道断了，就 200 ms → 400 ms → … 最长 5 秒地退避重试；
  提交失败的那一帧不会丢，下一轮原样重发（静态图不用干等 30 秒）。
- **不自动拉起后台服务，也不自动拉起自己**：宿主没跑的时候，服务端就在那儿等外部内容，
  屏幕保持设备原来的画面。

## 怎么用

```powershell
# 后台服务照常跑着，然后另开一个窗口：
cargo run -p lcl-display-host --release

# 只送一帧就退出（调试用）
cargo run -p lcl-display-host --release -- --once
```

宿主从命名管道读配置，所以**屏幕模式、路径、旋转这些还是在界面里改**，
改完宿主会在下一轮（≤1 秒）跟上。

界面上“屏幕”这一页的说明由服务端按配置给出（“主题：光环表盘”“图片：cat.png”…
守护进程不再解码媒体，所以不知道画面细节，只知道配置），预览图是最后推上屏的那一帧。

## 测试

```powershell
cargo test -p lcl-display-host
cargo test -p lcl-daemon
```

宿主侧的测试全是纯计算，不碰设备、不连管道：静态图复用、GIF 帧率上限、
主题重画条件、配置变了要重新读、提交失败要重发、超大文件要拒绝、
未托管不出帧。守护进程侧测的是描述文案、帧摘要和内嵌的透明 PNG 的头。

## 还没做的

- 帧率上限 5 fps 是保守值；真机确认稳定以后可以调 `MAX_FPS`。
- 宿主还没有开机自启、也没有被服务拉起来；现在只能手动跑。
- 内容只有主题 / 图片 / GIF 三种；视频（ffmpeg 转帧）还没接。
